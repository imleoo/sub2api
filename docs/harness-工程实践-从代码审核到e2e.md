# Harness 工程实践：从代码审核到 E2E 的全链路闭环验证

> 沉淀自 2026-06 一段贯穿生命周期的工程：
> **代码审核报告 → 计划对抗式交叉验证（v1→v6）→ workflow 分阶段执行 → 遗留待办 → 收尾清理 → 全功能 E2E**。
> 表面是一串前后相继的活，本质是同一件事在每个环节的重复：**用 harness 把"这步对吗"翻译成"这个检查绿吗"**。
> 全程出现了**四类不同的 harness**，它们接力构成一条完整验证链——这才是本文真正想讲的。
>

## 0. 全貌：一条贯穿生命周期的 harness 链

| 阶段 | 干什么 | 该环节的 harness | 门禁（绿的定义） | 产物 |
|-----|-------|----------------|----------------|------|
| ① 审核发现 | 找出逆向订阅死代码等问题 | （人/工具审核，本文不展开） | —— | 审核报告 + 原始清单 v1 |
| ② 计划硬化 | 把"能不能删"问清楚 | **对抗式交叉验证 harness** | 任一独立验证者都挑不出 Critical | 8 Critical 暴露 → 安全方案 v6 |
| ③ 执行 | 几十文件分阶段删改 | **编排 harness（workflow）** | 每阶段编译/测试 gate 绿才提交才进下阶段 | P2–P5 四提交；P6 测试红即停 |
| ④ 收尾清理 | 删剩余 inert 死代码 | **静态 harness（编译器/linter）** | `unused=0` + build/vet/unit/integration 绿 + rg 死符号清零 | T1 三类清理三提交 |
| ⑤ 行为验证 | 证明删完行为不变 | **动态 harness（E2E）** | 穿真实上游转发 200 + 计费/限额闭环 | 自包含 e2e 套件 |

一句话：**harness 不是"测试"的同义词，它贯穿"定计划 → 执行 → 验结构 → 验行为"的每一环**。每一环都把一个模糊问题压成一条机器可判的绿/红。

## 1. 理论框架：harness 是什么

**定义**：harness 是把「做 X / 这步对吗」翻译成「这个检查通过」的**闭环验证装置**。它把人脑里模糊的"应该对了"换成机器（或独立第三方）可判定的"绿/红"。

### 1.1 四要素

| 要素 | 含义 |
|-----|------|
| **目标 → 可验证标准** | 把"做 X"写成一条可机械判定的断言 |
| **反馈源** | 谁判绿/红（独立验证者 / 编排器 gate / 编译器&linter / 真实系统） |
| **迭代循环** | 红了改、改了再判，直到绿 |
| **分级门禁** | 不过当前关不许进下一关，失败即停 |

### 1.2 四类 harness（按生命周期排）

| 类型 | 出现阶段 | 反馈源 | 管什么 | 特性 |
|-----|---------|--------|-------|------|
| **计划硬化** | 执行前 | 独立/异构验证者（多模型/多工具 grep） | 计划安全吗（删了会不会塌房） | 便宜、纸面、靠"独立视角"发现盲区 |
| **编排** | 执行中 | 编排器的阶段 gate（编译/测试） | 大改动怎么安全推进 | 可恢复、可审计、失败即停 |
| **静态验证** | 改完 | 编译器 / `golangci-lint unused` / nilness | 结构正确（无死代码、编译过、类型闭合） | 快、确定、全程序可达性 |
| **动态验证** | 改完 | 真实上游 + 被测系统 | 行为正确（真转发、真计费、真拦截） | 慢、需环境、只覆盖跑到的 |

### 1.3 选型主线

> **计划阶段用对抗验证防塌房；执行阶段用编排控风险；改完用静态验结构、动态验行为。
> 静态绿永远证明不了行为对——改了热路径就必须接动态。**

## 2. 案例①：计划硬化 = 对抗式交叉验证 harness

### 2.1 问题
原始清单 v1 想「整删 `pkg/oauth/`、`gemini_token_cache.go`、`refresh_token_cache.go`…」。直接执行会**塌房**：这些目录里混着**正规功能**（用户登录 OAuth、Vertex/service_account、用户 Refresh Token）。

### 2.2 harness
不靠单一视角自检，而是**多个独立/异构验证者交叉验证计划**：
- **2 轮 Claude 静态验证** + **2 轮 Codex（codex-cli，独立 grep）交叉验证**。
- **门禁**：任一独立验证者发现 Critical → 整个清单判 **🔴 Red（不能执行）**，打回重修。

### 2.3 产出
对 v1 四方一致判 Red，揪出 **8 个 Critical**，例如：
- 删 `pkg/oauth/` 会断 `auth_linuxdo/dingtalk/oidc/wechat_oauth.go` 的 PKCE → **必须拆分保留**。
- 删 `gemini_token_cache.go` 会断 `claude_token_provider`/`gemini_token_provider`/`wire_gen` → **必须保 provider**。

迭代 v1→…→**v6 安全方案**（分阶段 + 精确切除边界 + 每阶段验证命令）。Codex 还独立补出若干 Claude 漏掉的点（`error_passthrough_rule.go`、`useOpenAIOAuth.ts` 等），并有 1 处 dispute 被采纳。

### 2.4 教训
- **高风险删除/重构，先用独立视角对抗验证「计划」，再动手**——纸面验证比线上事故便宜几个数量级。
- **异构 > 同构**：换一个模型、换一种工具（grep vs 语义）独立验证，能发现单一视角的系统性盲区。"自己验自己"几乎验不出自己的盲点。
- 门禁是「任一独立验证者发现 Critical 即 Red」，不是"多数通过"——安全问题一票否决。

## 3. 案例②：执行 = 编排（workflow）harness

### 3.1 问题
v6 方案 P2–P7 + 前端 PF，整删 ~50 文件、局部切除 ~60 文件。一把梭必翻车，怎么安全推进？

### 3.2 harness
用 **workflow 编排器**驱动执行，内建四条性质（执行报告原话）：**自动顺序执行、编译门禁、逐阶段提交、失败即停**。
- 每阶段（P2/P3/…）改完先过编译/测试 gate，**绿了才 commit、才进下一阶段**。
- 任一阶段 gate 红 → **编排器立即停**，不硬推。

### 3.3 产出
- 自动交付 **P2–P5 四个提交**（每阶段一个，gate 全绿）。
- **P6 停在测试 gate 红**：源码删除已完成（~40 文件删、~60 改），但 ~11 个测试用例的平台断言（4→3/去 antigravity）没同步 → gate 红 → 编排器按「失败即停」中止、**未提交**。
- 干净断点 → 人工/主线接手，只需同步那 ~11 个断言即转绿，再推 P7 + PF + 复核。

### 3.4 教训
- **编排 harness 的价值 = 可恢复 + 可审计 + 失败即停**。
- **逐阶段提交把"中途停止"变成"干净断点"而非"半成品泥潭"**：P6 停时前 4 阶段是 4 个独立、可回滚、gate 全绿的提交，接手者一眼知道在哪、缺什么。
- **失败即停 > 带病前进**：P6 红时编排器没有"绕过测试"硬推，而是停下交人——这正是 harness 该有的纪律。
- 编排器本身也是工程产物（`.claude/workflows/` 编排脚本），可复跑、可审计。

## 4. 案例③：收尾清理 = 静态 harness

### 4.1 目标可验证化
「清掉剩余 inert 死代码」翻译成门禁：
```
go build ./... && go vet ./...
go test -tags=unit ./internal/... && go test -tags=integration ./internal/...
golangci-lint run ./...        # unused 清零
rg 'tokenType == "oauth"|RequirePrivacySet|IsPrivacySet' backend/internal   # 死符号清零
```

### 4.2 反馈源：linter 的「传递闭包」
死代码删除有**级联**：删 A → 只被 A 用的 B 也死 → 只被 B 用的 C 也死……肉眼追不全。
`golangci-lint unused`（staticcheck U1000）做**全程序可达性分析**，一次算出整个传递闭包。

**最反直觉的一课**：`tryWriteOpenAIImagesStreamEvent` 我 grep 数到 **12 处引用**却被判 `unused`——那 12 处全在「同样 unused 的函数」内部，整簇从任何活入口不可达。
**信 linter 的可达性，别信 grep 计数**：grep 数"文本出现"，linter 算"从入口可达否"。

### 4.3 循环 + 分级门禁
删一批 → `go build` + 重跑 linter → 它报新冒出的孤儿 → 再删，直到 `unused=0`。
本次级联链：删 oauth 死分支 → `getBetaHeader` 死 → `mergeAnthropicBeta(Dropping)` 死 → 5 个 constants 死 → 相关测试死。
按风险低→高（类3→类2→类1）分阶段，**每阶段过全套门禁才提交、才进下阶段，失败即停**（与案例②同纪律）。

### 4.4 静态的边界 → 交棒动态
类 1 删完静态全绿，但 follow-up 拦了一道：「改网关热路径，**unit 兜不住转发行为正确性**，必须真实转发冒烟」——**静态到边界，须接动态**。

## 5. 案例④：行为验证 = 动态 harness（E2E）

### 5.1 自包含四步骨架
```
boot（dev_local 起服务）→ seed（admin API 造数据）→ run（go test -tags=e2e）→ teardown（trap 拆）
```
- `trap cleanup EXIT`：通过/失败/中断都拆；`BOOTED_SERVER` 标志位区分"自起自拆"与"连已有实例"。
- 双模式：`E2E_BASE_URL` 已设→连已运行实例；未设→自起自拆。覆盖本地调试 + CI。

### 5.2 灰盒：控制面 + 数据面
- **控制面（admin/user API）**：seed 账号/分组/key、建用户设余额、查余额/用量。
- **数据面（网关）**：穿被测网关发真请求。
- 断言 = 数据面行为（转发成功/被拦截）+ 控制面状态变化（余额扣减/用量入账）。

### 5.3 provisioning 放 Go，bash 只编排
复杂造数据放 typed Go helper（`sync.Once` 共享 + `requireProvision(t)` 懒取 + 环境不全 skip）；bash 只起服务/注入 env/跑 test/拆环境。

## 6. 衔接：四类 harness 如何接力（核心）

```
①对抗验证(计划)  ─Red→修→直到无Critical─→  安全方案 v6
        │（计划安全了，但还没动代码）
        ▼
②编排(workflow)  ─逐阶段gate/失败即停─→  P2–P5 安全落地（P6 干净断点交接）
        │（代码删了，结构对不对？）
        ▼
③静态(编译器/linter)  ─unused=0/级联删干净─→  结构正确
        │（结构对了，但"行为不变"证明不了）
        ▼
④动态(E2E)  ─真上游转发+计费对账─→  行为正确
```

- **每一棒都把上一棒"做完了"升级为"验过了"**：计划验安全 → 执行验落地 → 结构验编译 → 行为验运行。
- **跨棒的纪律是统一的**：可验证化 + 分级门禁 + 失败即停。案例②③用的是同一条「逐阶段、gate 绿才进、红即停」。
- **最值钱的认知**：③静态绿 ≠ ④行为对。class-1「必须 e2e 冒烟」就是这条原则的实例——**改了热路径/共享逻辑，别停在静态绿，把真东西跑一遍。**

## 7. 动态 harness 实操细节（踩坑 + 技法）

### 7.1 Shell / Bash 坑
- `${VAR:-default}` vs `${VAR-default}`：冒号版把"空串"也当默认（`E2E_RUN=""` 跑不了全部那个 bug）；要区分"未设/显式空"去掉冒号。
- 裸 `$VAR` 贴 CJK，`set -u`+C.UTF-8 报 unbound：`${VAR}` 加花括号 + ASCII 标点隔开。
- `set -o pipefail` 下管道 `$?` 抓的是最后一段：扫密用 `if … | grep …; then` 别接 `head`。
- 自动加载 gitignored env：`set -a; source "$ENV_FILE"; set +a`。

### 7.2 凭证管理（安全红线）
- 三件套：gitignored 真凭证（`script/e2e.env`）+ 提交模板（`.example`）+ harness 自动加载。
- `.gitignore` 路径陷阱：裸 `scripts` 匹配任意层级 → `backend/scripts/` 被忽略、根级 `script/`（单数）没被忽略。`git check-ignore -v` 双向确认。
- 提交前必扫暂存区凭证；`//go:build e2e` 隔离，单独 `go vet -tags=e2e` 做编译门禁。

### 7.3 测试设计（动态断言艺术）
- **上游不可控 → 容忍式 skip 而非 fail**：第三方 404/502 不是你的 bug。网关把上游非 200 如实回传，恰证明转发链路通（本次 count_tokens 404、gemini 502 都 skip）。
- **模型映射穿网关测**：直连上游 `gemini-2.5-flash` 404、穿网关 200——网关有模型规范化，结论以"穿网关"为准。
- **限额是"消费后检查" → sendUntilBlocked + 等异步落账**：第一次必过（used=0），消费后第二次才拦。
- **阈值语义精确 + 验证前置**：余额预检 `Balance <= 0`（非 `< 0`），把余额设成恰好 0，且先确认环境没发赠额（发了 skip）。
- **枚举值读 handler `oneof`**：`status` 合法值 `active|inactive`（不是 `disabled`），别猜。
- **计费弱断言 + 对账强校验**：不断言精确成本（脆），断言"扣了/没扣"；再用 `SUM(actual_cost)==初始-当前余额` 逐分钱对账验闭环。
- **优雅 skip 哲学**：环境不全 skip 不 fail（CI 友好）；区分 skip(无法构造/上游限制) 与 fail(我方坏)。

## 8. 共通原则（跨四类 harness）

1. **可验证化**：任何"做 X"先翻译成机器/独立第三方能判绿红的断言。
2. **选对反馈源**：计划安全用独立异构验证；执行风险用编排 gate；结构用编译器/linter；行为用真实运行。
3. **信全局分析，别信局部直觉**：独立交叉验证 > 自检；linter 可达性 > grep 计数；穿网关结果 > 直连探测。
4. **分级门禁、失败即停**：低风险先行、逐阶段提交、每关绿才进；红了停下交接，别带病前进。
5. **干净断点 > 半成品**：逐阶段提交让"中途停"变成可恢复的独立提交。
6. **容忍不可控**：依赖外部的部分，区分"我方故障"与"外部限制"，后者 skip。
7. **静态绿 ≠ 行为对**：改热路径/共享逻辑，静态只是必要条件，动态才充分。
8. **提交前自检**：扫凭证、build tag 隔离、`check-ignore` 确认。

## 9. 复用清单

**计划硬化（高风险重构/删除前）**
- [ ] 用 ≥2 个独立/异构视角（不同模型 + 不同工具 grep）交叉验证「计划」
- [ ] 门禁=任一视角发现 Critical 即打回；逐条落实到方案
- [ ] 明确"看着像但不能删"的保留清单（误删即破坏）

**执行编排（多阶段大改动）**
- [ ] 分阶段 + 每阶段编译/测试 gate + 逐阶段提交 + 失败即停
- [ ] 红了停下交干净断点，别绕过测试硬推
- [ ] 编排脚本留档可复跑

**静态验证（代码变更）**
- [ ] 目标写成门禁命令组；用 linter unused/可达性当级联探测器，删→build→重跑→再删
- [ ] 信可达性别信 grep 计数；改了热路径标记"需动态验证"

**动态验证（e2e/行为）**
- [ ] `trap cleanup EXIT` + `BOOTED_SERVER` + 双模式；自动加载 gitignored env + `.example`
- [ ] `check-ignore` 双向确认 + 提交前扫密 + build tag 隔离
- [ ] provisioning 放 Go；枚举读 handler `oneof`；上游非 200 区分 skip/fail
- [ ] 限额 sendUntilBlocked + 等异步落账；计费弱断言 + 对账强校验

## 10. 一句话心法

> **harness 是把"应该对了"换成"绿了/有人独立验过了"的装置——它贯穿定计划、执行、验结构、验行为每一环。**
> 计划安全吗，找独立视角对抗验；执行稳吗，分阶段 gate 失败即停；结构对吗，问编译器和 linter；行为对吗，把真东西跑一遍。
> **改了热路径，静态绿只是开始，别停。**
