## 0. 使用须知（先读）

1. **行号可信度**：标了具体行号区间的，是 Codex/rg 实测命中点；标「**施工时打开文件确认**」的，表示该位置范围会随改动漂移或需人工判断，执行时必须打开文件核对，**不要照抄行号盲删**。

## 2. P1 解耦细则（最易塌房，单列）

### 2.1 Gemini service_account project_id 自动探测解耦

- 现状：`gemini_token_provider.go:114-126` 的 `auto_detect_project_id` 调用 `p.geminiOAuthService.fetchProjectID(...)`。
- **风险归因订正（v6）**：service_account 路径在 `gemini_token_provider.go:60` 处即 `return`，**根本到不了 `:114` 的 auto-detect 分支**。所以 auto-detect 是**纯 OAuth 路径专属逻辑**，删它**不影响**正规 service_account。这段反而是逆向代码，应删。（v5 把它描述为"删会断 service_account"是错误归因，照此保留 `fetchProjectID` 等于留下逆向残留。）
- 方案 A（推荐）：**直接删除 auto-detect 分支与 `fetchProjectID` 调用**。service_account 接入本就显式给 project_id，正规路径无依赖。
- 做完后 `gemini_token_provider.go` 构造器去掉 `*GeminiOAuthService` 参数（`:18-38`），并把 `:56` 的允许守卫从 `OAuth || ServiceAccount` 收敛为仅 `ServiceAccount`，同步改 Wire（§4）。

### 2.2 OpenAI 网关构造器解耦

- `openai_gateway_service.go:367,429` 字段/构造器持有 `*OpenAITokenProvider`。
- P1 先改 `NewOpenAIGatewayService` 签名去掉该参数（OAuth token 分支随 P3 删），Wire 同步（§4）。

### 2.3 pkg/oauth PKCE 工具抽离

- 用户登录直接用 `oauth.GenerateState/GenerateCodeVerifier/GenerateCodeChallenge`（命中：`auth_linuxdo_oauth.go:91,128,133`、`auth_dingtalk_oauth.go:123`、`auth_email_oauth.go:67`、`auth_oidc_oauth.go:124,161,166,172`、`auth_wechat_oauth.go:105,343`、`auth_oauth_pending_flow.go:105`）。
- P1 先把这三个工具函数（及它们依赖的最小类型）保留在 `pkg/oauth` 或迁到新的 `pkg/oauth/pkce.go`；P5 只删 Claude 逆向专属的 `SessionStore`/`OAuthSession`/`TokenResponse`/URL 构造。

## 附录 B. 背景与边界

本项目 fork 自开源 AI 网关，**原玩法**：拿别人的 Claude Code / Codex(ChatGPT) / Gemini CLI / Antigravity 订阅账号，OAuth 逆向登录换 token，在网关层伪装成官方客户端转卖订阅额度。本方案目标是**彻底删除订阅逆向**，改为正规 API 接入。三类「看着像但不能删」的代码见 §0.3（用户登录 OAuth / 面板自有订阅配额 / 正规云接入 Vertex·Bedrock·apikey 直通）。

**已核实不存在的文件**（历史清单误列，勿找）：`claude_max_subscription_service.go`、`account_oauth_metadata.go`、`account_oauth_refresh.go`、`token_provider_oauth.go`、`account_usage.go`、`service/account_validation.go`、`admin_account_service.go`（相关逻辑实际散落在 `admin_service.go`、`account_test_service.go`、`handler/admin/account_handler.go`）。
