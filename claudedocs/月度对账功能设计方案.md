# 月度对账功能设计方案（Vendor Report）

> 状态：方案待评审，未实施
> 需求来源：`docs/需求/Vendor report template - Eonreach (1).xlsx` + `docs/需求/代理商对账接口协议.md`
> 已确认口径（2026-07-18）：余额取数用「反推法 + 月结快照表」两者结合；对账范围为完整资金流水（全复刻模板六种行）

---

## 1. 需求理解

### 1.1 Excel 模板解读

模板是**单账户单月的资金对账单**，10 列、按日期排的流水行，共六种行类型：

| 行类型（Nature） | 含义 | 涉及列 |
|---|---|---|
| A/C Opening balance | 期初余额 | Total |
| Deposit | 充值 | Deposit/(Withdraw) USD |
| Withdraw | 提现/退款 | Deposit/(Withdraw) USD（负数） |
| Credit | 赠送/兑换入账 | Credit USD |
| Utilisation | 按日消耗 | Qty(A) × Unit Price(B) = 折前成本(C)，× Discount rate(D) → 折后成本(C×D 列，实际是 `C×(1−D)`) |
| A/C Closing balance | 期末余额 | 各列 SUM + Total |

关键特征：
- **Total 列是逐行滚动余额**（`=上行Total + 本行变动`），期末行对上一切流水。
- Utilisation 行的 Qty 为负数（消耗），Unit Price 是单价，Discount rate 是折扣率。
- 金额单位 USD。

### 1.2 功能点

1. **用户端**：新增「月度对账」页面，选月份查看对账单 + 导出 Excel（格式复刻模板）。
2. **管理端**：用户管理列表每行「更多」菜单增加「对账导出」，管理员可导出任意用户任意月份的对账单。

## 2. 现状调研结论（决定方案形态的约束）

### 2.1 数据模型：无统一资金流水表 ⚠️

余额是 `users.balance`（`decimal(20,8)`）**原地更新**，全库没有账变流水表、没有 `balance_after` 快照。资金变动分散在 5 张表：

| 变动类型 | 表 | 关键字段 | 模板行映射 |
|---|---|---|---|
| 充值 | `payment_orders` | `user_id, amount, order_type='balance', status, paid_at`（硬删除） | Deposit |
| 退款 | `payment_orders` | `refund_amount, refund_at` | Withdraw |
| 优惠码赠送 | `promo_code_usages` | `user_id, bonus_amount, used_at` | Credit |
| 兑换码 | `redeem_codes` | `type='balance', value, used_by, used_at` | Credit |
| 企业划转 | `team_fund_transfers` | `owner/member_user_id, direction(grant/reclaim/auto_topup), amount, created_at`（无 users 外键台账） | Deposit/Withdraw（对成员而言） |
| 消费 | `usage_logs` | `user_id, total_cost(倍率前), actual_cost(倍率后=实际扣款), rate_multiplier, *_tokens, created_at`（只追加） | Utilisation |

> 注意管理端已有的「余额历史」（`GET /admin/users/:id/balance-history`）实际返回的是兑换码记录，**不是**余额账变流水，不能复用。

### 2.2 计费字段与模板列的映射

- `total_cost` = 倍率前标准计费 → **Cost (before discount)**（C 列）
- `actual_cost` = `total_cost × rate_multiplier` = 实际扣款 → **Cost (after discount)**（I 列）
- 折扣率 D = `1 − actual_cost/total_cost`（聚合后反算；`rate_multiplier<1` 为优惠）
- Qty(A) 列 → 当日 token 总量（负数）；Unit Price(B) → `total_cost/qty` 反算的等效均价。模板的 A×B=C 恒等式由反算保证成立。
- `usage_logs` 已有 `(user_id, created_at)` 复合索引，按天聚合可用现成 `GetDailyStatsAggregated`（`internal/repository/usage_log_repo_stats.go:189`），但需扩展 SQL 增加 `SUM(total_cost)`（现只 SUM 了 actual_cost）。

### 2.3 工程现状

- **无 Excel 库**：`go.mod` 无 excelize，需首次引入 `github.com/xuri/excelize/v2`。现有导出先例是 CSV（`internal/handler/admin/redeem_handler.go:391-464`，header 写法可照抄）。
- **无 `/api/v1/bill/*`**：协议文档里的 balance/logs 接口尚未实现（本方案不做，只做对账单；两者数据口径应保持一致，未来实现 bill 接口时复用本方案的聚合层）。
- 路由：用户端挂 `internal/server/routes/user.go` 的 `/usage` 组；管理端挂 `admin.go` 的 `registerUserManagementRoutes`（`/admin/users`）。
- 前端：管理端「更多」菜单在 `src/views/admin/UsersView.vue:669-761`（Teleport 弹层，非独立组件）；blob 下载先例 `src/api/admin/redeem.ts:180-192`（`responseType: 'blob'`）。

## 3. 总体设计

### 3.1 余额口径：反推法 + 月结快照（已确认）

- **新表 `balance_snapshots`**：一行 = 单用户单月，存期初/期末余额 + 四类流水汇总。月结定时任务在每月 1 日凌晨为上月落快照；`(user_id, period)` 唯一，可幂等重算。
- **反推法兜底**：查不到某月快照（历史月、新部署首月）时，service 实时反推：
  ```
  期末余额(M) = users.balance 当前值 − Σ(M 月之后至今的净变动)
  期初余额(M) = 期末余额(M) − M 月净变动
  净变动 = 充值 − 提现/退款 + 赠送 + 划转净额 − Σactual_cost
  ```
  反推结果**不落库**（避免污染精确数据），响应中带 `source: computed|snapshot` 标记，前端注明「系统反算值」。
- 恒等式校验：`closing = opening + deposit − withdraw + credit − utilisation`，快照单行自校验；对不平时报表脚注提示差额（手工改余额等未留痕操作会体现在这里）。

### 3.2 对账范围：完整六种行（已确认）

- Deposit 行：`payment_orders`（`order_type='balance'` 且已支付，按 `paid_at` 归月）逐笔 + `team_fund_transfers` grant/auto_topup（成员视角）逐笔。
- Withdraw 行：`payment_orders.refund_amount`（按 `refund_at`）+ `team_fund_transfers` reclaim 逐笔。
- Credit 行：`promo_code_usages` + `redeem_codes(type='balance')` 逐笔。
- Utilisation 行：`usage_logs` **按天聚合**（模板即按天一行），列出 Qty/等效单价/折前/折扣率/折后。
- 首尾 Opening/Closing 行 + Total 滚动余额列。

### 3.3 时区与 T-1

- 对账月界按请求 `timezone` 参数解析（默认服务端时区），与协议文档 §5.6 对齐。
- **当月**允许查看但标注「未封账」（数据到 T-1）；导出文件名带 `-partial` 后缀。

## 4. 数据层设计

### 4.1 新表 `balance_snapshots`（Ent schema + 手写迁移）

```
id                       BIGSERIAL PK
user_id                  BIGINT NOT NULL          -- 不建 FK，台账语义（同 team_fund_transfers）
period                   VARCHAR(7) NOT NULL       -- 'YYYY-MM'，字典序即时间序
opening_balance          DECIMAL(20,8) DEFAULT 0
closing_balance          DECIMAL(20,8) DEFAULT 0
deposit_total            DECIMAL(20,8) DEFAULT 0
withdraw_total           DECIMAL(20,8) DEFAULT 0   -- 存正数量级，方向由列名表达
credit_total             DECIMAL(20,8) DEFAULT 0
utilisation_gross_total  DECIMAL(20,10) DEFAULT 0  -- Σtotal_cost 折前
utilisation_total        DECIMAL(20,10) DEFAULT 0  -- Σactual_cost 折后（正数）
computed_at              TIMESTAMPTZ DEFAULT now()
UNIQUE (user_id, period); INDEX (period)
```

- 新增 `ent/schema/balance_snapshot.go`（参照 `channel_monitor_daily_rollup.go` 的 rollup 模式），`go generate ./ent`。
- 迁移 `migrations/183_add_balance_snapshots.sql`（当前最新 182，embed glob 自动发现）。

### 4.2 月结定时任务

- 新增后台服务 `internal/service/balance_snapshot_service.go`：每月 1 日 00:30（服务端时区）遍历活跃用户，为上月 upsert 快照；期初取上月快照的 closing（无则反推）。
- 挂入 Wire cleanup 生命周期（同现有定时报告/清理服务模式）；`go generate ./cmd/server`。
- 管理端提供手动重算入口（见 §5.2），首次上线可对历史月按需补算。

### 4.3 Repository 扩展

- `usage_log_repo_stats.go`：`GetDailyStatsAggregated` 增加 `SUM(total_cost)` 输出（或新增专用方法，避免动现有调用方）。
- 新增 `balance_snapshot_repo.go`：Upsert / GetByUserPeriod / ListByUser。
- 新增聚合查询（分别在各自 repo 或统一放 statement 专用 repo）：
  - `payment_orders`：按 user + 月区间列已支付订单、退款；
  - `promo_code_usages` / `redeem_codes`：按 user + 月区间列赠送；
  - `team_fund_transfers`：按 member_user_id + 月区间列划转。

> 分层约束：Service 不能 import Repository 之外的层，golangci-lint 强制；聚合入口统一走新的 `StatementService`。

## 5. 后端 API 设计

### 5.1 用户端（JWT，挂 `/api/v1/usage` 组）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/usage/statement?month=2026-05&timezone=Asia/Shanghai` | 返回结构化对账单 JSON（页面渲染用） |
| GET | `/api/v1/usage/statement/export?month=...&timezone=...` | 返回 xlsx 文件流 |
| GET | `/api/v1/usage/statement/months` | 返回可查月份列表（注册月起至当月） |

响应 `data` 结构（statement）：

```json
{
  "period": "2026-05",
  "source": "snapshot | computed",
  "closed": true,
  "opening_balance": 1000.0,
  "closing_balance": 3120.5,
  "rows": [
    { "date": "2026-05-01", "nature": "deposit",     "amount": 5000.0, "note": "订单 PO2026..." },
    { "date": "2026-05-02", "nature": "utilisation", "qty": -20000, "unit_price": 0.05,
      "cost_before": 1000.0, "discount_rate": 0.4, "cost_after": 600.0 },
    { "date": "2026-05-04", "nature": "withdraw",    "amount": -1000.0, "note": "退款" },
    { "date": "2026-05-06", "nature": "credit",      "amount": 10.0, "note": "兑换码" }
  ],
  "totals": { "deposit": 5900.0, "withdraw": 1000.0, "credit": 10.0,
              "utilisation_before": ..., "utilisation_after": ..., "identity_gap": 0.0 }
}
```

`identity_gap` = 恒等式差额，非 0 时前端脚注提示。

### 5.2 管理端（AdminAuth，挂 `/api/v1/admin/users`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/admin/users/:id/statement/export?month=...` | 导出指定用户对账单 xlsx |
| POST | `/api/v1/admin/users/:id/statement/recompute?month=...` | 手动重算该月快照（可选，二期） |

沿用 admin 中间件链（鉴权 + 审计 + ComplianceGuard）；导出会进 audit_logs（敏感读取）。

### 5.3 分层落位

- `internal/service/statement_service.go`：核心聚合（六种行拼装、反推、恒等式校验）。用户端/管理端 handler 共用。
- `internal/pkg/xlsxreport/`：**独立 Excel 生成包**（excelize 组装、模板样式复刻），service 只返回结构化行数据，不依赖 excelize——参照现状「CSV 内联在 handler」但 Excel 逻辑更重，抽包更干净。
- handler：`internal/handler/statement_handler.go`（用户端）+ `internal/handler/admin/user_handler.go` 加导出方法（或独立 admin statement handler）。
- 导出 header 照抄 redeem CSV 先例：`Content-Disposition: attachment; filename=statement-{email}-{2026-05}.xlsx`，MIME `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`。

### 5.4 新依赖

`github.com/xuri/excelize/v2`（纯 Go、Apache-2.0、无 CGO，embed 构建不受影响）。

## 6. Excel 生成（复刻模板）

- Sheet1 布局逐格复刻：`Vendor report` 标题、`Period: May 2026`、A/B/C=A×B/D/C×D 列组说明行、双行表头（列名 + 单位）。
- 公式照写（`=E8*F8`、`=G8*(1-H8)`、`=C8+I8`、期末行 `=SUM(...)`），让导出文件在 Excel 里保持可审计的活公式，而非写死数值。
- 日期列写 date 类型 + `yyyy-mm-dd` 格式；金额列数值格式 `#,##0.00`；Utilisation 折前折后保留更多小数位。

## 10. 风险与已知取舍

1. **手工改余额不留痕** → 恒等式 gap 兜底暴露，但无法归因到具体日期；根治需全站账变埋点（超出本期范围，快照表已为其预留结构）。
2. **payment_orders 硬删除**：若运营删除历史订单，历史月反推会失真；快照落库后不受影响（快照优先正是为此）。
3. **等效单价是反算值**：同日多模型混合时 Unit Price 是加权均价，非任何单一模型牌价；模板 A×B=C 恒等式仍成立。表头可加注释说明。
4. **上游同步冲突面**：全部为新增文件，仅 `user.go/admin.go` 路由注册、`UsersView.vue` 菜单、`usage_log_repo_stats.go` 聚合扩展四处触碰共享文件——合并冲突面小，但需登记入功能列表风险表。
5. 协议文档的 `/api/v1/bill/*` 未实现，本方案不含；实现时应复用 StatementService 聚合口径，避免两套对账数字。
