## 2. 当前备份现状：结论是"没有任何生效中的备份"

逐项核实结果：

1. **应用内置备份功能已开发完成，但从未配置启用**
   代码里已经有完整实现：`backend/internal/service/backup_service.go` + `backup_pg_dumper.go` + `backup_s3_store.go` + 管理后台 `BackupView.vue`，支持 PostgreSQL `pg_dump` → gzip → 上传 S3 兼容对象存储（R2/OSS/COS 等）、cron 定时任务、按天数/份数保留策略。
   但查询生产库 `settings` 表：
   ```sql
   select key, length(value) from settings where key ilike '%backup%';
   -- (0 rows)
   ```
   `backup_s3_config` 和 `backup_schedule` 均无记录 → **这个功能从代码上线以来从未被管理员配置过**，没有任何自动备份在跑。

2. **系统级定时任务里没有业务备份**
   - `ubuntu` 用户 crontab 为空
   - `root` crontab 只有腾讯云 stargate agent 的心跳任务
   - `/etc/cron.d` 下都是系统自带项（sysstat、e2scrub 等），没有自定义备份脚本
   - `systemctl list-timers` 里同样没有备份相关 timer

3. **1Panel 面板级备份未配置**
   `/opt/1panel/backup` 目录存在但完全为空 —— 1Panel 在这台机器上只用来管理 openresty 反代，没有开启面板自带的备份计划。

4. **Redis 持久化配置存在漂移**
   `docker-compose.local.yml` 里已声明 `--appendonly yes --appendfsync everysec`，但该容器已连续运行 7 周未重启，`redis-cli CONFIG GET appendonly` 实测返回 `no`——说明当前生效配置是修改前的旧值，实际只靠默认 RDB 快照兜底（`redis_data/` 下也确实只有 `dump.rdb`，没有 AOF 目录）。好在 Redis 里目前只有 1177 个 key（多为缓存/限流/会话类数据，具体业务含义建议你确认一下），风险等级远低于 PostgreSQL。

**综合结论**：一旦这台 VM 出现磁盘故障、误删、被入侵或服务商侧事故，`sub2api` 数据库（用户、API Key、计费、用量等核心业务数据，393MB）以及 `config.yaml` 中的 `JWT_SECRET`、`TOTP_ENCRYPTION_KEY`、数据库密码等配置，**目前没有任何恢复手段**。

## 3. 风险评估

| 风险点 | 影响 |
|---|---|
| 单点故障：数据库/Redis/配置全部在同一块系统盘 | 磁盘损坏 = 数据全丢 |
| 无异地副本 | 服务商侧机房级事故无法恢复 |
| 无自动化、无监控告警 | 即使配置了备份，没跑成功也不会有人知道（需要配合校验） |
| `JWT_SECRET` / `TOTP_ENCRYPTION_KEY` 未备份 | 配置丢失会导致全站会话失效、2FA 全部失效，影响业务连续性（不算数据丢失，但等同于一次全站强制下线） |
| 数据库含计费/订单相关表 | 丢失后资损无法追溯，是这套系统里优先级最高的备份对象 |

## 4. 推荐方案（按优先级排序）

### 方案 A（首选，成本最低，代码已就绪）：启用系统自带的备份功能

系统已经内置了完整的 PostgreSQL 备份能力，只是没打开开关：

1. 准备一个 S3 兼容对象存储 bucket（推荐 Cloudflare R2 或腾讯云 COS 的 S3 兼容接口，同地域上传通常免流量费）
2. 管理后台「备份管理」页填写 `Endpoint / Bucket / AccessKeyID / SecretAccessKey`，点「测试连接」
3. 设置定时策略：建议每天凌晨执行（如 `0 2 * * *`），`retain_days` 建议 14~30 天
4. 手动触发一次「立即备份」，确认能成功生成并上传，再核对文件大小是否与 `pg_size_pretty` 数量级吻合

**局限**：这套功能只覆盖 PostgreSQL，不包含 Redis、`.env`、`config.yaml`、`docker-compose.local.yml` 这些配置和密钥文件，需要方案 B 补齐。

### 方案 B：补充配置与密钥的异地备份

方案 A 覆盖不到的部分：`/opt/sub2api/deploy/.env`、`deploy/data/config.yaml`、`deploy/docker-compose.local.yml`（三者都在仓库 `.gitignore` 里，从未进入过版本控制或任何备份）。

建议思路（**尚未实施，需要你确认后再动手**，因为涉及在生产机上新增定时任务）：

```bash
#!/usr/bin/env bash
set -euo pipefail
SRC="/opt/sub2api/deploy"
DATE=$(date +%F)
TMP="/tmp/we2ai-config-${DATE}.tar.gz"

tar czf "$TMP" -C "$SRC" .env data/config.yaml docker-compose.local.yml
gpg --batch --yes --passphrase-file /root/.backup_pass --symmetric "$TMP"
rclone copy "${TMP}.gpg" "remote:your-bucket/we2ai-config/"
rm -f "$TMP" "${TMP}.gpg"

# 本地也顺手清理超过 7 天的临时文件
find /tmp -maxdepth 1 -name "we2ai-config-*.tar.gz*" -mtime +7 -delete
```

关键点：**必须加密**，因为这几个文件里明文含数据库密码、JWT/TOTP 密钥。

### 方案 C：Redis 数据的取舍

先确认 1177 个 key 是否都是可重建的缓存/限流/会话数据：
- 如果确认是纯缓存性质 → 不必单独备份，只需要让 `appendonly yes` 真正生效即可（需要重启 `sub2api-redis` 容器，会有几秒中断，建议低峰期操作）
- 如果不确定是否有不可再生数据 → 建议先把当前 `redis_data/dump.rdb` 复制归档一份，再评估

### 方案 D：整机快照兜底

在腾讯云控制台为这台 VM 的云硬盘配置定期快照策略，作为应用层备份（A/B）之外的最后一道兜底，能覆盖操作系统层面的问题。这一步只能在你的云账号里操作，我这边没有云账号权限，需要你自己或授权我登录控制台后再处理。
