## 1. 背景

管理后台「模型折扣」（`/admin/model-pricings`）与用户端「模型广场」（`/api/v1/models`）显示的模型集不一致。运营经核对确认：广场显示的模型经反查都在账号 `model_mapping` 中可调用，**广场口径正确**，后台口径偏窄。这构成业务漏洞——存在用户可调用但运营在后台看不到、无法定价的模型。

## 2. 现状代码梳理

### 2.1 两端共用数据源

| 项 | 来源 |
|---|---|
| catalog（内存快照） | `PricingService.buildCatalogAndAliasIndex` → `modelPricingRepo.LoadAllEnabled` 仅加载 `model_pricings.is_enabled=true`（`pricing_service.go:199-228`） |
| 后台列表 | 直接查询 `model_pricings` 表（`repository/model_pricing_repository.go:236-338`） |

**结论**：两端最终都源于 `model_pricings.is_enabled=true`，差异来自过滤层叠加方式。

### 2.2 现有差异点

| 维度 | 后台 `visible_only=true` | 模型广场 `/api/v1/models` |
|---|---|---|
| 数据源 | `model_pricings` 表 | `pricingService.ListAllModels()` = catalog 快照 |
| 账号范围 | 所有 `deleted_at IS NULL` 账号（**不区分 status**） | 仅 `account.IsActive()`（status='active'）且属于当前用户可访问 group 的账号 |
| 命中规则 | `accounts.credentials->model_mapping` key 精确匹配或前缀通配（`repository/model_pricing_repository.go:285-303`） | 同上，**额外**：generic 平台走 `endpoint.SupportedModels` 并集，空白名单兜底 catalog 全部启用模型（`usage_handler.go:622-643`） |
| 海外开关 | handler 层按 `show_overseas_models=false` 整段排除前缀（`handler/admin/model_pricing_handler.go:178-183`） | 前端二次过滤：海外前缀 + claude<4.5 / gpt<5.2 / gemini<3 / o1~o4（`ModelsView.vue:275-280, 394-429`） |
| `is_custom` 维度 | 与 `visible_only` 通过同一组 filter 暴露给用户筛选；用户当前选了「自定义」→ 与「可见」语义被混淆 | 不涉及 |

### 2.3 用户场景对照

用户截图：广场 66 条、后台 12 条全部为 `自定义` 标签且全部是 lingjing/kling 视频/图片模型。
- 12 条差集 = 用户在后台选了 `来源=自定义` 这个**与可见性正交的过滤**。
- 54 条差集 = 同步自上游的 LLM 模型，全部 `is_custom=false`。

这是**根因之一**：UI 把「来源」与「可见性」叠在一起当默认条件。

## 3. 统一目标（已达成一致）

1. **后台必须 ⊇ 广场**：任何用户能调到的模型，运营都必须能在后台看到、定价、打折。
2. **两端不强求集合相等**，但需满足单调包含关系：
   - 后台「可见」= **运营视角**：catalog ∩ 任意 active 账号可路由
   - 广场「可见」= **当前用户视角**：后台口径 ∩ 当前用户可访问的 group/账号
3. **海外开关只作用于「用户广场」展示，后台始终看全集**。
4. **「来源（is_custom）」与「可见性」彻底解耦**。
5. **孤儿/异常模型置顶 + 红色标注**，让运营主动发现并修正。

## 4. 关键问题代码侧定性

### 4.1 「is_enabled=true 但所有账号都禁用」的产生路径（5.1）

`model_pricings` 与 `accounts` 两条配置链完全解耦：

- catalog 生成：仅读 `is_enabled=true`，与账号状态无关（`pricing_service.go:203`）。
- 账号 status 为 `active / disabled / error`（`domain/constants.go:5-7`），独立管理，**不会触发 model_pricings 反向同步**。
- 运营实际流程：
  1. 同步上游价格 → 写入 `model_pricings`（`is_custom=false`，默认 `is_enabled=true`）
  2. 挂载账号被禁用/报错/到期被踢出调度
  3. 无 watchdog 把「无活跃账号」状态反写到价格表

后台当前 `visible_only` SQL **只校验 `deleted_at IS NULL`**，未校验 `status='active'`（`repository/model_pricing_repository.go:291-293`）。因此后台会把「靠禁用/报错账号挂载」的模型仍判为可见——这是修复点之一。

### 4.2 广场显示 ¥0.00 的真正成因（5.2）

并非「未配价」，而是**展示口径 bug**。但成因比"前端 else 分支算错"更深一层——**bug 主要在后端 DTO 层，不在前端**：

**(a) DTO 层把 PricingUnit 坍缩成 token**

`/api/v1/models` 的数据源是 `PricingService.ListEnabledCatalogModels`（`pricing_service.go:1072-1110`），它构造下发用的 `ModelInfo` 时：

```go
PricingUnit: ModelPricingUnitToken,                 // 默认 token（1085）
if entry.PricingUnit == ModelPricingUnitSecond {    // 只有 second 被保留（1089）
    info.PricingUnit = ModelPricingUnitSecond
}
```

`image_generation / video_generation` **从未被赋值，全部 fall through 成 `token`**。前端根本拿不到这两个 unit 值。

**(b) DTO 不含单张/单视频价格字段**

下发结构 `service.ModelInfo`（`pricing_service.go:1016-1026`）只有 `InputCostPerToken / OutputCostPerToken`，**不含** `CustomInputCost / CustomOutputCost / OutputCostPerImage / OutputCostPerImageToken`。前端 TS 类型 `api/models.ts:14-26` 同样写死 `pricing_unit: 'token' | 'second'`，没有这些字段。

**(c) 前端 else 分支只是被动受害者**

`ModelsView.vue:189-211` 确实只判 `second` / else，但即使它新增 image/video 分支，也**无价格字段可读、无 unit 值可判**——所以这是 (a)(b) 的下游症状，不是根因。

**(d) 价格究竟存在哪个字段：当前有三个候选，必须先盘点**

- seed 生图模型用 `OutputCostPerImage`（`model_catalog_seed.go:182-198`）；
- 静态视频模型用 `OutputCostPerImageToken`（`pricing_service.go:41-50`）；
- 文档早期假设的 `CustomInputCost / CustomOutputCost` 多数情况下为 NULL。

这意味着 §5.3 判定**不能**简单用 `custom_*_cost IS NULL`（会把 seed 数据全判成错配）。**Step 0 已实测确认承载字段（见 §4.4），结论：价在 `output_cost_per_image` / `output_cost_per_image_token`，`custom_*_cost` 全 0。**

含义：
- 现有"价格为 0"现象**不是缺失数据**，是后端 DTO 丢了 unit + 价格字段后前端按错单位渲染。
- 修复需要 **后端 service 映射 + 契约扩展 + 前端渲染** 三处协同，**不是纯前端改动**（详见 §5.4 与 §6 修订后的风险评级）。
- **现成范式**：`second` 单位已用 `CustomInputCost → InputCostPerToken` 的方式下发（`pricing_service.go:1098-1100`），前端 `formatSecondUsdPrice` 直接读 `input_cost_per_token`（`ModelsView.vue:540`）。image/video 照此办理即可，**无需新增 DTO 字段**，只需保留 PricingUnit 并把对应价格装入 input/output 字段。

### 4.3 海外开关分组化（5.3）的可行性

现状：
- `show_overseas_models` 是**全局 setting**（`setting_service.go:1211`、`settings_view.go:205`）。
- `Group` schema 无 `allow_overseas_models` 字段（`backend/ent/schema/group.go`）。
- catalog 本身不含海外过滤；海外过滤现在散落在：
  1. `handler/admin/model_pricing_handler.go:178-183`（应去除）
  2. `ModelsView.vue:275-280, 394-429`（应下沉至 service 层）

两种实现路径：

| 路径 | 描述 | 改动量 | 推荐度 |
|---|---|---|---|
| **A. Group 加 `allow_overseas_models`** | ent schema + 迁移 + Group CRUD + 前端表单 + service 聚合 | 大 | 后续增量 |
| **B. 全局开关只作用广场展示，后台始终看全集** | 去 admin handler 那段过滤；广场过滤从前端下沉到 `ListVisibleForUser` | 小 | **本轮采用** |

**B 路径的语义**：「限制分组」通过运营手段实现——给只想用海外/只想用国产的用户分配不同 group，复用已有 group×account 路由模型，无需额外 schema。未来若要细化再上 A。

### 4.4 Step 0 数据盘点实测结论（2026-06-06，本地 `uds` 库 317 行 / 全 enabled）

实测数据**推翻了 §4.2 早期假设**，并暴露原方案未覆盖的数据治理工作。结论如下：

1. **`pricing_unit` 零区分度**：317 行**全部** `=token`，连 image/video 模型也是。→ 前端/DTO **不能按 `pricing_unit` 分支**，真正的判别维度是 **`mode`**（`image_generation` / `video_generation` / `chat` / `embedding` / ...）。

2. **价格列无单一规则**（按 mode 交叉，enabled）：

   | mode | 行数 | 价在 `output_cost_per_image` | 价在 `output_cost_per_image_token` | 价在 token 列 |
   |---|---|---|---|---|
   | image_generation | 28 | 22 | 10 | 10（重叠） |
   | video_generation | 41 | **35** | 2 | 1 |
   | chat / responses / audio_* / embedding | 其余 | 4（**污染**） | 0 | 走 token |

   - `custom_input_cost / custom_output_cost` **全 0** → §4.2 早期"价格在 `Custom*Cost`"假设**作废**。
   - 同家族列都不统一：`doubao-seedance-1.5-pro`（价在 `output_cost_per_image`）vs `doubao-seedance-1.5-pro-10s`（价在 `output_cost_per_image_token`）。
   - 注意 image_generation 实际含**两种计价模型**：seedream 系=单张定价（`output_cost_per_image`）、gpt-image 系=按图片 token 定价（`output_cost_per_image_token`）。**决策已定：分列保留**——不合并成一列，两列各承载一种语义（见下）。

   **canonical 列约定（决策：分列）**：
   - `output_cost_per_image` = **按次/单位**计价（每张图、每个视频/每秒等"一次产出一口价"），USD。
   - `output_cost_per_image_token` = **按输出 token** 计价的图片/视频模型，USD per token。
   - 每行依其真实计费模型**只填其一**（迁移与导入器都遵守）。前端据"哪列非空 + mode"决定单位文案（单张价 / 按 token 价）。

3. **真正未配价的 enabled 行仅 5 条**（按 mode 应有的列全空）：`deepseek-v3-2-251201`(chat)、`gemini-flash-experimental`(embedding)、`HappyHorse-1.0` / `S2V-01` / `v6`(video)。→ `missing_pricing` 判定**必须 mode-aware**。

4. **数据污染**：4 个 `gemini-3.1-pro-*`（mode=chat）带 `output_cost_per_image=0.00012`（疑似 token 价误写入图片列并 ×10 错位），需清理。

5. **重复变体且价格冲突**：`doubao-seedance-1-5-pro`(img=0.01099) / `doubao-seedance-1.5-pro`(img=0.02954) / `Doubao-Seedance-1.5-pro`(img=0.01099)——大小写 + `-`/`.` 变体造成重复行、价差近 3 倍，需去重。

6. **NULL vs 0**：未配价列为 **NULL**（非 0）。判定统一用 `coalesce(col,0)=0` 覆盖 NULL/0 两种，§8 该决策点关闭。

**决策（已确认）**：采用「**先清洗迁移、再改显示**」——见 §7 新增 Step 0.5。清洗后 `pricing_unit` 与价格列恢复可信，§5.3 / §5.4 可写干净规则而非容脏兜底。

### 4.5 价格数据来源与导入链（Step 0 脏数据的根因）

`model_pricings` 表的价格由**三条相互独立、约定不一致的导入链**写入，这正是 §4.4 脏数据的产生原因——**脏在导入器，不在表本身**。

| 来源 | 文件 | 路由 / 入口 | 币种 | 写入约定（实测） |
|---|---|---|---|---|
| 海外模型（LiteLLM） | `backend/data/model_pricing.json`（GitHub 同步） | `POST .../sync-from-upstream` | USD | LiteLLM 原生字段，图片价在 `output_cost_per_image_token`；**部分 chat 模型自带 `output_cost_per_image`**（→ §4.4 的 4 条 `gemini-3.1-pro-*` 污染） |
| 万界方舟 | `backend/data/wanjie.json`（embed + 远端） | `POST .../sync-from-wanjie`（`convertWanjieModel`，`wanjie_sync.go:121`） | **RMB→USD** | 图片（¥/张 modal `2-2-2`）**与**视频/音频（¥/秒 modal `2-4-1/2-4-7`）**都塞进 `output_cost_per_image`**（`wanjie_sync.go:189-200` 复用同一列）；`ModelID = 原始 ModelName`（→ `Doubao-Seedance-1.5-pro` 大小写变体） |
| 火山引擎豆包 | `backend/data/doubao.json` | **本轮新增** `POST .../sync-from-doubao`（待实现，决策已定接通） | RMB→USD | 当前走 `model_catalog_seed.go` 硬编码（`doubao-seedream-*` / `doubao-seedance-1.5-pro`）；接通后改由 doubao 导入器写入，沿用 §4.5 归一约定 + 6.8 汇率换算，逐步替代硬编码 seed |

**根因 = 三套约定打架**：
1. **列约定不一**：LiteLLM 用 `output_cost_per_image_token`、万界用 `output_cost_per_image`（图/视频都塞这列）、seed 也用 `output_cost_per_image` → 解释了 §4.4「价格分散在两列、同家族不统一」。
2. **model_id 不归一**：万界用原始 ModelName，seed/lingjing 用自己的 id → seedance 大小写/标点重复行冲突。
3. **LiteLLM chat 模型自带图片价字段** → 4 条 chat 污染。

**关键结论（升级 Step 0.5 范围）**：**一次性清洗迁移不够**——只要不改导入器，下次 `sync-from-wanjie` / `sync-from-upstream` 就会按旧约定重新写脏。**必须同步给导入器加归一层**（canonical 列 + canonical model_id 大小写/标点），否则治理无法持久。

### 4.6 RMB→USD 汇率链（万界/豆包专属风险）

- 万界导入按 `v = cnyVal / cnyRate` 换算（`wanjie_sync.go:151`）。**字段语义统一为 USD**。
- **汇率冻结在导入时刻**：换算只在 sync 那一次发生，事后修改系统汇率**不会重算**已入库的 USD 价。改汇率后，旧行（按旧汇率）与新行（按新汇率）口径分裂。
- **默认汇率已统一为 `6.8`**（决策已定，代码已改）。改动点：`config.go:1774` `pricing.cny_rate`、`wanjie_sync.go:58` `DefaultWanjieCNYRate`、`pricing_service.go:1053` `GetCNYRate` 兜底、`setting_service.go:3472` 默认值，以及 `api_contract_test.go:885,1144` 契约 fixture。`SyncFromWanjie` 实际取 `pricingService.GetCNYRate()`（DB 设置优先，回退 config 6.8，`model_pricing_handler.go:531-533`）。
- ✅ **lingjing 硬编码价已消除"第二汇率"（决策已定，代码已改）**：原 `pricing_service.go:24,28,33` 的 `¥0.2 / 7.28` 与 seed 的 ÷7 已全部改为 **`RMB 源价 / DefaultWanjieCNYRate`**（单一汇率口径）。改后值：seedream `0.2/6.8=$0.02941`、seedance per-sec `0.215/6.8=$0.03162`、seedance 5s/10s `1.075|2.150 / 6.8`（后两者仅喂已死的 `matchLingjingModel`）。比原 7.28 口径高约 7%。**注意**：seed 只影响新写入行；存量 DB 行仍是旧值，需 Step 0.5 迁移统一（见下）。
- **遗留（Step 0.5C）**：存量已入库行（万界/lingjing/豆包）仍是各自导入时刻的旧汇率冻结值。是否在迁移里按 6.8 统一重算所有 RMB 来源行，是唯一仍 open 的计费决策。

## 5. 修订后的统一方案

### 5.1 服务层（SSOT）

```
PricingService（新增/修订）
├─ ListCatalogAll()                  所有 is_enabled=true，无任何可见性过滤
│                                    → 后台 visible_only=false 走这里
├─ ListVisibleForOperator()          B 口径：catalog ∩ 任意 active 账号能路由
│   ├─ 含 generic.endpoint.supported_models 路径（从 usage_handler 抽出）
│   └─ 不应用海外开关（运营要看全集）
│                                    → 后台 visible_only=true 走这里
└─ ListVisibleForUser(userID)        C 口径：B ∩ 用户可访问 group/account
    └─ 应用海外开关 + 版本下限（从前端下沉）
                                     → /api/v1/models 走这里
```

### 5.2 Repository 层

`ModelPricingRepository.List` 的 `visible_only=true` SQL 增加约束：

```sql
-- 当前：仅 a.deleted_at IS NULL
-- 修正后：
WHERE a.deleted_at IS NULL
  AND a.status = 'active'
```

修复 4.1 中「禁用/报错账号挂载也算可见」的假阳性。

### 5.3 派生 `pricing_health` 字段（service 层计算）

> 判定**以 `mode` 为准**（Step 0 实测 `pricing_unit` 无区分度）。清洗迁移（§7 Step 0.5）后 `pricing_unit` 会回填为可信值，届时两者等价；在迁移完成前一律读 `mode`。

| 状态 | 判定（`is_enabled=true`，按 `mode`） | 含义 |
|---|---|---|
| `missing_pricing`（token 类） | `mode ∉ {image_generation, video_generation}` ∧ `coalesce(input_cost_per_token,0)=0` ∧ `coalesce(output_cost_per_token,0)=0` | 文本/embedding 等未配价（实测 5 条之一类） |
| `missing_pricing`（图片/视频类） | `mode ∈ {image_generation, video_generation}` ∧ `coalesce(output_cost_per_image,0)=0` ∧ `coalesce(output_cost_per_image_token,0)=0` | 图/视频模型未配任何单价（实测 `HappyHorse-1.0`/`S2V-01`/`v6`） |
| `unit_contamination` | `mode='chat'`（或其它文本类）∧ `coalesce(output_cost_per_image,0)<>0` | 文本模型被误写图片价（实测 4 条 `gemini-3.1-pro-*`） |
| `orphan_no_active_account` | 在 `ListCatalogAll` 集合中但不在 `ListVisibleForOperator` 集合中 | 启用了价格但无活跃账号挂载 |
| `ok` | 其余 | 正常 |

> 说明：原 `unit_mismatch`（"非 token 未配特殊单价"）已被上表「图片/视频类 `missing_pricing`」取代，语义更准；并新增 `unit_contamination` 对应实测污染行。`coalesce(col,0)=0` 统一覆盖 NULL 与 0（Step 0 结论 ⑥）。
>
> ⚠️ **`orphan_no_active_account` 与分页的交互**：该状态是 `ListCatalogAll \ ListVisibleForOperator` 的**集合差**，无法在 repo 的单行 SQL 内计算（`List` 分页返回每页 20 条，`model_pricing_repository.go:324-328`）。正确实现：service 先**一次性物化** operator-visible 的全量 `model_id` 集合（`map[string]struct{}`），再对当前页逐行 O(1) 标注——**不要**做成每行一次 EXISTS 查询的 N+1。

## 7. 上线顺序（灰度）

**前置约束**：

1. `visible_only` SQL 加 active 约束后，**当前后台能看到的「自定义模型挂在已禁用账号」一类条目会消失**，会让运营误以为数据丢了。
2. **孤儿展示与 `visible_only` 过滤天然冲突**：孤儿一旦被 `a.status='active'` 过滤掉，就**不可能**再出现在 `visible_only=true` 列表里。而 admin handler 当前默认 `visibleOnly=true`（`model_pricing_handler.go:151`）。若不改默认值，Step 3 之后默认视图永远看不到孤儿，红标无处可挂，直接违背目标 3.5。
   → **后台默认列表必须切到 `visible_only=false`（全集 = `ListCatalogAll`）**，孤儿才能带红标置顶；`visible_only=true` 退化成「只看真正可路由」的可选筛选。这也更贴合目标 3.1「后台 ⊇ 广场」。

必须按以下顺序：

0. **Step 0（数据盘点）✅ 已完成**：实测结论见 §4.4。核心：`pricing_unit` 全 token（弃用为判别维度，改用 `mode`）；图/视频价分散在 `output_cost_per_image` / `output_cost_per_image_token`；存在 4 条 chat 污染 + seedance 重复变体；未配价用 NULL 表示。
0.5. **Step 0.5（数据清洗迁移 + 导入器归一，新增·实现前置阻断项）**：

   **(A) 一次性迁移**（`repository/migrations_runner.go` 体系内）治理存量 `model_pricings`：
   1. **回填 `pricing_unit`**：`mode='image_generation' → 'image_generation'`、`mode='video_generation' → 'video_generation'`，其余保持 `token`（让 pricing_unit 重新可信，前端可直接按它分支）。
   2. **价格列归一（分列约定，见 §4.4）**：图/视频行按计费模型把价格放进正确的列——按次/单位价 → `output_cost_per_image`，按输出 token 价 → `output_cost_per_image_token`，**每行只填其一**；对 seedance 这类同模型双填的，以正确档位为准、清空另一列。
   3. **清污染**：清空 `mode ∈ {chat, responses, embedding, ...}` 行误填的 `output_cost_per_image`（实测 4 条 `gemini-3.1-pro-*`）。
   4. **去重变体**：合并 `doubao-seedance` 大小写/标点重复行，保留正确价格那条，停用/删除其余（注意先确认正确档位价，见 §8）。
   > 迁移必须**幂等 + 可回滚**（先 `SELECT` 导出受影响行存档，再 `UPDATE`）。

   **(B) 导入器归一（关键，否则 (A) 被下次 sync 冲掉）**——见 §4.5 根因。给三条导入链加统一归一层：
   1. **model_id 归一**：导入时统一大小写/标点（如全小写 + `.`→`-`），杜绝万界 `ModelName` 与 seed id 产生重复变体。
   2. **价格列约定统一（分列）**：万界 `convertWanjieModel`（`wanjie_sync.go:189-200`）当前图/视频都塞 `output_cost_per_image`——视频若是按秒/按次属"按次价"可留此列，但需与 LiteLLM 的 `output_cost_per_image_token`（按 token 价）语义对齐到 §4.4 分列约定，每行只填其一。
   3. **过滤源头污染**：LiteLLM 导入时，非图片 mode 不写 `output_cost_per_image`。
   4. **新增 doubao 导入器（本轮决策）**：`backend/data/doubao.json` → `sync-from-doubao`，RMB→USD 按 6.8（`GetCNYRate`）换算，复用 1-3 的归一约定；逐步替代 `model_catalog_seed.go` 里硬编码的豆包价（迁移期两者并存需防 model_id 冲突，故 model_id 归一是前提）。
   > (A) 治存量、(B) 防新增，**两者必须同批上线**，否则清洗无法持久。doubao 导入器（B.4）与万界/LiteLLM 归一同批。

   **(C) 汇率口径**（见 §4.6）：确认系统实际 `cnyRate`（代码默认 7，待核对是否 6.8）；评估是否需要在 sync 时对**全部** RMB 来源行按当前汇率统一重算，避免新旧行汇率分裂。
1. **Step 1（仅展示，无行为变更）**：后台默认视图切到 `visible_only=false`（全集）；service 层产出 `pricing_health`（`orphan_no_active_account` + `missing_pricing` + `unit_contamination`），前端置顶 + 红色徽标。此时 SQL 未变，运营在全集列表上能直接看到「这条没活跃账号 / 没配价 / 单位污染」。
2. **Step 2（前端解耦 + 单位渲染修复）**：先上线 **5.4.0 后端 DTO 修订**（保留 image/video unit + 装价格），再上线 ModelPricingsView 默认筛选解耦、ModelsView 按 PricingUnit 分支渲染。两端同批，否则前端分支命不中。
3. **Step 3（修正 visible_only SQL）**：`visible_only=true` 分支增加 `a.status='active'`，删除 admin handler 海外过滤。因默认视图已是全集 + 孤儿红标预热过，运营有心理准备。
4. **Step 4（C 口径下沉）**：广场 `/api/v1/models` 切到 `ListVisibleForUser`，从前端移除版本/海外过滤（同时统一 o 系列前后端判定）。
5. **Step 5（监控期）**：观察 1-2 周，确认无运营反馈「东西突然不见」，再清理 `ModelsView.vue` 中遗留的过滤死代码。
