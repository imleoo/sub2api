### ✅ 1.1 响应流无条件遮蔽 — 已修复（保守门控）

- **改法**：响应侧品牌词遮蔽 `maskResponseBody` 全部加 `account.IsResponseMaskingEnabled()` 门控；两处流式路径在循环外计算一次 `needMask`。

## 1. P0 — 立即修复（并发安全与正确性）

> ✅ **本章两项均已于 2026-06-10 修复并验证**，落地细节与纠偏见 §0.1。以下保留原始计划口径供追溯。

### 1.1 [9.1] 用量缓存共享指针 data race — ✅ 已修复

- **位置**：`backend/internal/service/account_usage_service.go:779-786`
- **根因**：缓存命中快速路径在 singleflight 锁外，直接对存放于全局 `sync.Map` 的共享 `*UsageInfo` 原地写 `usage.FiveHour.RemainingSeconds`。并发请求同账号时与其它写入/下游 JSON 序列化构成 data race。
  ```go
  usage := cache.usageInfo            // 浅拷贝指针，指向共享对象
  if usage.FiveHour != nil && usage.FiveHour.ResetsAt != nil {
      usage.FiveHour.RemainingSeconds = int(time.Until(*usage.FiveHour.ResetsAt).Seconds()) // 原地写共享内存
  }
  return usage, nil
  ```
- **修复**：命中后对 `UsageInfo` 及内嵌 `FiveHour` 指针做浅拷贝，再计算 `RemainingSeconds`，返回副本。Antigravity / Anthropic 两条缓存命中路径都要改（含 singleflight 内二次命中 `recalcAntigravityRemainingSeconds`）。
- **验证**：`go test -race -tags=unit ./internal/service/...`；补一个并发命中缓存的 race 测试。
- **口径修正**（采纳第三份报告）：二审"开 `-race` 直接 panic 崩溃"措辞过强。准确说法是 race detector 会报告并使测试失败，生产不一定 panic，但行为在 Go 内存模型下不安全。

### 1.2 [1.1] 响应流无条件遮蔽 + 开关未覆盖响应侧 — ✅ 已修复（保守门控）

- **位置**：`gateway_service.go:7845`（主 SSE 流）、`5601-5602`（passthrough 流）、`gateway_response_masking.go:232`（`maskResponseBody`）；开关 `account.go:1547` `IsResponseMaskingEnabled()` 当前**仅**被 `gateway_service.go:4481`（请求侧身份拦截）引用。
- **根因**：两类缺陷并存——
  1. **性能**：流循环每个 block 无条件 `maskResponseBody(reverseToolNamesIfPresent(...))`，`maskResponseBody` 无条件 `responseTextReplacer.Replace(string(body))`，长流式响应产生大量 `[]byte↔string` 堆分配。
  2. **语义正确性**（更关键）：`IsResponseMaskingEnabled` 开关不读响应侧，导致**未开启遮蔽的账号其输出中的 `AWS/Amazon/亚马逊` 也被强制改写为 `Anthropic`**。
- **修复**：
  - 进流循环前计算一次 `needMask := account != nil && account.IsResponseMaskingEnabled()`，仅 `needMask` 为 true 才遮蔽。
  - `replaceAllBytes` 改用 `bytes.Contains`/`bytes.ReplaceAll` 避免 string 来回转换。
  - **单独确认**（采纳第三份报告）：工具名还原（静态 `sessions_`/`session_`）可能属于协议兼容，不一定该绑定 response masking 开关，需与产品确认后再决定是否同样门控。
- **验证**：补测试覆盖"未开启遮蔽账号响应含 AWS 不被改写""开启账号正常遮蔽"两条；`go test -tags=unit ./internal/service/...`。

## 2. P1 — 本轮修复

### 2.1 [9.2] `AccountService.Update` 分组校验前置 / 事务化

- **位置**：`backend/internal/service/account_service.go` — `accountRepo.Update` 在 `:294`，`RequireOAuthOnly` 校验在 `:305`，`BindGroups` 在 `:313`。
- **根因**：主表 `Update` 先落库，之后才校验 apikey 账号是否被绑定到 `RequireOAuthOnly` 分组；校验失败 / `BindGroups` 失败都不回滚，留下脏写。
- **修复**：最小改法把 `RequireOAuthOnly` 校验前置到 `:294` 之前；完整改法把主表更新与 `BindGroups` 包进同一 DB 事务。
- **口径修正**（采纳第三份报告）：脏写范围**不止** Credentials——`:249-284` 中所有在请求里传入并于 `Update` 前赋值的字段（`Name/Notes/Credentials/Extra/ProxyID/Concurrency/Priority/Status/ExpiresAt/AutoPauseOnExpired`）都可能已落库。
- **验证**：补"apikey 账号绑 RequireOAuthOnly 分组应整体失败且无脏写"用例。

### 2.2 [2.1] SSE scanner 64KB buffer 复用池

- **根因**：`sse_scanner_buffer_pool.go` 已提供 `getSSEScannerBuf64K/putSSEScannerBuf64K`，原生路径 `handleStreamingResponse` 已复用，但下列 compat / forward-as 路径仍每请求 `scanner.Buffer(make([]byte, 0, 64*1024), ...)` 新分配 64KB。
- **位置（按第三份报告全仓口径，共 10 处，非二审所述 9 处）**：
  - `gateway_forward_as_chat_completions.go:232`、`:379`
  - `gateway_forward_as_responses.go:241`、`:390`
  - `openai_gateway_messages.go:500`、`:681`
  - `openai_gateway_chat_completions.go:460`
  - `openai_gateway_chat_completions_raw.go:274`
  - `openai_gateway_responses_chat_fallback.go:330`
  - `antigravity_gateway_service.go:4333`（Antigravity 流路径，二审遗漏）
- **修复**：改为复用池。**关键**：goroutine 内消费 buffer 的路径（keepalive/超时分支），`put` 必须放进读取 goroutine 的 `defer`，参照原生路径，不能用顶层 defer，否则提前归还导致数据竞争。
- **建议分批**：先覆盖 OpenAI/Claude compat 9 处，再单独评估 Antigravity 1 处。

### 2.3 [8.2] `BulkUpsertMaas` N+1 + 非事务半写

- **根因**：同步 MaaS 模型定价时逐行查询/更新（N+1），且无事务包裹，中途失败留下半写。属定价数据一致性问题，优先级高于普通性能项。
- **修复**：参照已有 `UpsertBatch` 的"一次批量读取 → 分组过滤 → 批量 Upsert（CreateBulk+OnConflict）"模式，并用事务包裹。
- **验证**：`go test -tags=unit ./internal/repository/...`。

### 2.4 [9.3] Gemini 用量无缓存 + 串行查询

- **根因**：`getGeminiUsage` 完全无缓存，且 daily / minute 两次 `GetAccountWindowStats` 串行无依赖。
- **修复**：加 ~1 分钟短内存缓存；两次聚合查询用 `errgroup` 并行。
- **验证**：补缓存命中 / 并行用例。

## 5. 🔒 审计盲区 — 安全专项（三份报告 0 覆盖，需补审后再修）

> **重要**：以下不是"已审计的待修项"，而是三份报告**未扫描的范围**。报告类别分布为「性能 50 / 冗余 15 / 质量 12 / 缺陷 8 / 可维护性 7」，**"安全"类别为 0**；`internal/handler`（100 文件）、`internal/middleware`、`internal/server/routes`、前端均零引用。对一个管理 API Key、加密凭证、多方支付、多渠道 OAuth 的网关，这是最大的修复前提缺口。**修复前须先完成专项审计确认具体缺陷，再排期。**

### S1. 多渠道 OAuth handler 安全性（handler 层，0 覆盖）
- **范围**：`auth_dingtalk_oauth.go`、`auth_email_oauth.go`、`auth_linuxdo_oauth.go`、`auth_oidc_oauth.go`、`auth_wechat_oauth.go`、`auth_oauth_pending_flow.go`
- **已知现状（非缺陷，待审）**：state 走 cookie 比对做 CSRF（如 `auth_dingtalk_oauth.go:322-324` `state != expectedState → "csrf"`；`auth_email_oauth.go:123-124` 同构）。
- **待审计点**：state 生成熵与时效、cookie 的 `Secure/HttpOnly/SameSite` 属性、`redirect_uri` 白名单、绑定流程（pending flow）的会话固定 / 账号接管风险、错误重定向是否泄露信息。

### S2. 限流 / 熔断中间件（middleware 层，0 覆盖）
- **位置**：`internal/middleware/rate_limiter.go:79-116`
- **已知现状**：Redis Lua 限流，默认 `RateLimitFailOpen`（`:86-87`）——**Redis 故障时放行全部请求**。
- **待审计点**：该 fail-open 默认是否符合防滥用预期、限流 key 维度是否可被绕过、与入口鉴权的关系。报告 Module 3 谈的是 service 层 singleflight 缓存，**与这个真正的入口闸门不是一回事**。

### S3. 支付回调验签正确性（payment，仅点状抽查）
- **位置**：5 个 provider 的 `VerifyNotification` — `alipay.go:278`、`airwallex.go:222`(+`verifyAirwallexWebhookSignature:487`)、`easypay.go:238`、`stripe.go:173`、`wxpay.go:426`
- **现状**：报告仅覆盖 EasyPay 签名空值过滤（11.3 误报）与 wxpay refund 多查（11.4），**未系统检查验签正确性**。
- **待审计点**：伪造回调 = 免费充值，是支付集成最高危攻击面。需检查时间戳重放窗口、签名算法与密钥来源、金额 / 订单号 / 状态的一致性校验、`return_url` 与 `notify_url` 的信任边界。

### S4. handler 越权 / 鉴权（admin 与 gateway handler，0 覆盖）
- **范围**：`internal/handler/admin/*`、`gateway_handler*.go`、`api_key_handler.go` 等
- **待审计点**：管理员接口的越权访问（IDOR）、API Key 校验路径、用户态 / 管理态边界。

### 安全专项建议执行方式
建议另起一轮 `--focus security` 审计，范围限定 `internal/handler`、`internal/middleware`、`internal/payment/provider/*.VerifyNotification`，产出第四份**安全审计报告**后再把确认的缺陷并入本修复报告的 P0/P1。优先级应**高于** §3 的 Low 级性能微优化。
