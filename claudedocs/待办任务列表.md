## ✅ T1.5 · 模型白名单选择器搜不到新同步模型（已完成）

**状态**：✅ 已完成（2026-07-01）
**登记日期**：2026-07-01（发现与修复同一会话完成）

**根因**：`GET /api/v1/admin/model-pricings` 的 `List()`（`backend/internal/handler/admin/model_pricing_handler.go:180-254`）无条件按"广场可路由集合"做交集过滤（`filter.VisibleOnly=true` + `RoutableModelIDs`），这个设计对"模型定价管理页"（`ModelPricingsView.vue`，功能34"后台=广场"口径）本身合理，但 `ModelWhitelistSelector.vue`（账号编辑弹窗的白名单选择器）复用了同一个接口当候选源——它要展示的恰恰是"已同步定价数据、但还没被任何账号引用过"的模型，这批模型正好被广场口径过滤排除，形成循环依赖：新模型永远搜不到，因为它还没被任何账号选中过。

**修复**：
- `model_pricing_handler.go`：`List()` 新增 `for_whitelist=true` 查询参数，命中时跳过广场可路由集交集过滤，只保留 `is_enabled` 等其它过滤条件。默认行为（不带该参数）不变，不影响「模型定价管理页」。
- `frontend/src/api/admin/modelPricings.ts`：`ModelPricingListFilter` 补 `for_whitelist?: boolean` 字段。
- `frontend/src/components/account/ModelWhitelistSelector.vue`：`fetchModels()`/`fillRelated()` 两处调用均带上 `for_whitelist: true`。

**测试**：`model_pricing_handler_test.go` 新增 `TestModelPricingHandlerListForWhitelistSkipsRoutableFilter`（两个子用例：默认仍套广场口径 / `for_whitelist=true` 跳过过滤），后端 `go test -tags=unit`、前端 `typecheck`/`lint:check` 均通过。

**关联文档**：无独立功能号（属于功能 24/34 模型定价链路的 bug 修复，未改变其设计口径）。

## ✅ T2 · Gemini 生图计费：未产出图片场景仍计费 1 张图（已修复）

**状态**：✅ 已完成（2026-07-01）
**登记日期**：2026-07-01
**发现路径**：用户询问 e2e 是否覆盖生图模型计费 → 排查 `ModelWhitelistSelector.vue` 白名单选择器 bug 过程中顺带发现。

**根因**：`backend/internal/service/gemini_messages_compat_service.go` 的 `Forward()`（约 L989-992）、`ForwardNative()`（约 L1462-1465），以及 `gemini_chat_completions_compat_service.go` 的 `forwardClaudeBodyAsChatCompletions()`（约 L263-266），三处统计 `imageCount` 的逻辑完全相同：

```go
imageCount := 0
if isImageGenerationModel(originalModel) {
    imageCount = 1
}
```

只要请求模型名命中 `isImageGenerationModel()`（`gateway_temp_unschedule.go:40-51`，白名单 `gemini-2.5-flash-image*`/`gemini-3-pro-image*`/`gemini-3.1-flash-image*`），**无论上游实际返回了什么都硬编码记 1 张图**——代码完全没有解析响应体里 `inlineData`（图片 part）的数量，也没看 `finishReason`。

**影响**：Gemini 生图模型对涉及人物、版权、暴力等内容有安全策略，经常返回 HTTP 200 但 `finishReason=SAFETY`、无 `inlineData`（请求"成功"但没图）；也可能出现模型被要求"只回复文本不生成图片"而真的照做的场景。这两类情况下用户会被**错误扣费/扣配额，但实际没拿到任何图片产出**。

**不受影响的部分**：计费公式本身（`billing_service.go:876 CalculateImageCost()` = 单价 × 数量）与定价数据（`model_pricings.output_cost_per_image`）均正确，问题仅在于喂给公式的 `imageCount` 这个数字来源不对。对比之下 OpenAI 生图路径（`openai_images.go:654-712`）是正确实现——会解析响应里的实际图片数覆盖默认值，Gemini 这边是退化实现，两条链路不一致。

**修复**：
- 新增共享 helper `countGeminiGeneratedImages(geminiResp map[string]any) int`（复用已有的 `extractGeminiParts`，统计 `candidates[0].content.parts` 里带 `inlineData` 的 part 数）和字节版本 `countGeminiGeneratedImagesFromBytes`（供尚未解析成 map 的原生透传路径用），均在 `gemini_messages_compat_service.go`。
- `Forward()`/`ForwardNative()`/`forwardClaudeBodyAsChatCompletions()` 三处硬编码全部改为使用解析结果；涉及的 6 个响应处理函数（非流式 ×3、流式 ×3）均改造为额外返回实际图片数：`handleNonStreamingResponse`、`handleNativeNonStreamingResponse`、`handleChatCompletionsNonStreamingResponseFromGemini` 新增 `int` 返回值；`geminiStreamResult`/`geminiNativeStreamResult` 结构体新增 `imageCount` 字段，在各自的 SSE 逐 chunk 解析循环里累加；`collectGeminiSSE`（供两处 `useUpstreamStream` 分支复用）新增 `int` 返回值，同样逐 chunk 累加而非只看最终聚合结果（避免图片出现在非最后一个 chunk 时漏计）。
- 计费公式和定价数据本身未改动，只改了喂给公式的 `imageCount` 来源。

**测试**：
- 单测（mock 上游，确定性，`backend/internal/service/gemini_messages_compat_service_test.go`）：3 条代码路径各 2 个用例（安全拦截零产出应计 0 / 实际产出应计 1）——
  `TestGeminiMessagesCompatServiceForward_{SafetyBlockedImageBillsZero,ActualImageBillsOne}`、
  `TestGeminiMessagesCompatServiceForwardNative_{SafetyBlockedImageBillsZero,ActualImageBillsOne}`、
  `TestGeminiForwardAsChatCompletions_{SafetyBlockedImageBillsZero,ActualImageBillsOne}`，共 6 个，全部 PASS。
- e2e（真实上游，`backend/internal/integration/e2e_full_gemini_image_billing_test.go`）：`TestE2EFull_GeminiImageBillingOnNoImageProduced` 断言从"零产出应被计费≥$0.01"反转为"零产出不应达到该阈值"。2026-07-01 用真实 Gemini 生图账号验证：修复前余额下降 $0.0585（误计费 1 张图），**重启服务加载新代码后**复测降为 $0.0000082（纯 token 成本），PASS。

**踩坑记录**：验证时第一次仍复现了旧行为（余额下降 $0.0585，和修复前一致），排查发现是本地 `dev_local.sh` 起的 Go 后端进程从改代码前就一直跑着（Go 编译型语言不像前端 Vite 有热重载），`./script/e2e-test.sh` 检测到"已有健康服务"就直接复用了旧二进制。`./script/dev_local.sh down && up` 重启后端后才验证通过。**后续改了后端 Go 代码后跑 e2e，务必确认服务已用新代码重启，不能依赖脚本的"自动复用已有服务"逻辑。**
